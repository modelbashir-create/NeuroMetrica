# NeuroMetrica Workspace Architecture 2.2 (Frozen)

This document is the source of truth for structure, MVVM boundaries, and file responsibilities.
It is written to be AI-agent friendly: explicit trees, per-file roles, and clear ownership rules.

Architecture 2.2 introduces no behavioral, API, or runtime changes. It exists only to record the current workspace structure following the ChromaImagingCore refactor.

Architecture 2.2 is the authoritative reference for future development, testing, audits, and regulatory documentation.

This workspace uses a dual-style architecture by design. The App target and Swift packages follow Apple and Swift best practices (MVVM, SwiftPM layout, public/internal separation). The ITKBridge native layer intentionally follows a medical PACS-style decomposition, prioritizing traceability, auditability, and explicit DICOM semantics over Apple idioms. This split is intentional and correct, and PACS-style structure is confined to imaging IO and native code only.

Architecture 2.2 guarantees that all DICOM semantics (grouping, ordering, geometry validation, provenance) are confined to ITKBridge. Geometry validation and diagnostics are read-only and must never modify image data, slice order, orientation, or spacing. ITK is the authoritative source of truth for image geometry and pixel data, and Swift layers must consume geometry exactly as provided.

Architecture 2.2 reasserts strict layering across App → Core → Engine → Imaging packages. Violating these boundaries requires a future architecture revision (2.3+) and must not be treated as an incremental refactor.

Architecture 2.2 is frozen. Any cross-layer changes or semantic shifts require a new architecture version and explicit documentation.

Guiding rules
- Strict MVVM in the app target: Views depend on ViewModels and state, never on engine or IO.
- Apple HIG aligned UI structure and behavior.
- Clear layering: App -> Core -> Features -> Engine Packages.
- Core services hide engine, file IO, and logging details from Features.
- Packages provide imaging IO/engine (ChromaImagingCore, ChromaEngineKit) and ML runtime (RedEngine).
- Launch screen is static (UIKit-only); loading screen is app-owned UI.

4) Controls

Viewer interactions (macOS + iOS)
- Active viewport: click/tap a viewport to make it active.
- Toolbar tools: select an active tool (Window/Level, Pan, Zoom, Measure, Cine).
- Slice navigation:
  - Scroll/two-finger scroll over a viewport changes slices.
  - Drag vertically when not in Zoom mode scrubs slices.
  - Keyboard: up/down arrows step slices; page up/down jump by 5; home/end jump to first/last.
- Zoom:
  - Pinch (trackpad) zooms the active viewport.
  - Command + scroll zooms in/out on macOS (plain scroll remains slice navigation).
  - When Zoom tool is active, vertical drag zooms (drag up = zoom in, drag down = zoom out).
  - Zoom is per-viewport and clamped to sane bounds in ViewerState.
- Cine:
  - Space toggles cine playback for the active viewport.
  - Left/right arrows adjust cine FPS.

Responsibilities (per file)
- Package.swift

Core/
- ChromaEngine.swift
  - High-level engine facade: ITK descriptor -> CImageVolume conversion, metadata parsing, slice extraction.
  - CPU path remains authoritative; GPU is optional and must fall back safely.
  - Debug-only GPU/CPU comparison hook for parity validation.
  - Slice output contract: CIImage2D grayscale uint8, componentsPerPixel=1, bytesPerRow=width.
  - WW/WL operates on raw stored voxel values (no rescale slope/intercept).
  - GPU Geometry Contract:
    - GPU consumes CImageVolume.voxelData in ITK-produced order with native spacing/origin/direction.
    - No reordering, canonicalization, axis flipping, or geometry correction in GPU paths.
    - Validation metadata is read-only and used only for logging/diagnostics.

8) MVVM Boundaries (Quick Reference)

- Views:
  - Live under Features/*/Views.
  - Read state from ViewModels or ViewerState.
  - Never import ChromaEngineKit or ChromaImagingCore directly.
- ViewModels:
  - Live under Features/*/ViewModels.
  - Own business logic and call Core services (ChromaEngineBridge, FilePickerService, RecentFilesStore).
- Models:
  - Live under Core/Models or Features/*/Models.
  - Represent app or feature domain state and DTOs.
- Core Services:
  - Live under Core/Services; hide engine and IO details.
- Packages:
  - Provide the imaging and ML substrate; app does not depend on their internals directly.
